
## 踩过的坑

### 1. if/else-if/else 是单行道
进了 `n<0` 分支重读 n，控制流**回不去** else 分支——重读的 n 没人消费，
程序沉默退出。想"直到合法才放行" → 用 while 循环把关，不是 if。

### 2. 嵌套块内不许声明同名局部变量
else-if 里写 `int n = sc.nextInt()` → `Duplicate local variable n`，编译直接报错。
Java 比想象中严格：这条规则直接堵死了"新 n 活不过花括号"那类坑。
正确写法：去掉 `int`，赋值给外面的变量。

### 3. 无声逻辑错 vs 崩溃
- n=0 时程序**不崩**，但输出错误结果（擂主吃掉了用户根本没打算给的数）
- EOF 时崩 `NoSuchElementException`（Scanner 没数据可取）

**崩的反而好排查**（有堆栈、有行号），无声的错才是毒。
没异常 ≠ 没错。测试要专门喂非法输入（0、负数、EOF）。

### 4. 擂主初始化的教训
擂主 = 0，全负输入时永远输出 0 → **初值必须来自真实数据**，不是拍脑袋的常数。

## 设计决策（不只是代码对错）

n=0 有两种处理，都"对"，但要**有意识地选**：
- 退出版：尊重用户"我真的有 0 个数"（求最大值时 0 个数没有答案 → 提示退出合理）
- 重问版：0 视为误操作，逼用户给正数

同款场景预演：agent 收到工具参数 `count=0`，是执行还是打回？
**参数校验的每个分支都是设计决策。**

## 环境怪象（VS Code + Eclipse 编译器）

- 代码带编译错也能跑，运行到错行才抛 `java.lang.Error: Unresolved compilation problems`
- 编译失败后运行的可能是**旧 .class 残影** → 看到诡异输出先怀疑跑的不是最新版

## 安全支线为什么放后面（复述结论）

1. **相通**：注入=拼字符串，越权=条件写漏。基础不牢只能背口诀，看不出哪行代码会漏
2. **代价不对称**：本地小程序犯错免费（终端一红重跑五秒）；安全实践场地是真实环境，
   错误不可逆。免费场地练判断力，再上真场地
3. **注意力有限**：写安全代码要多想一层"输入不可信"。第一层（擂主、边界）还没成本能，
   两层一起想必然两层都糊

今天这题就是安全第一课：**永远假设用户会输入 n=0、n=-2、猫踩键盘。**
